# pr

作業中の変更を検証し、ブランチ経由でPRとして共有する。

## ワークフロー

1. `git status` / `git diff` で変更内容を確認する。コミット対象外のファイル
   （`.env` 等の秘匿情報）が紛れていないか確認する。

2. `npm run build` を実行し、エラーが出ないことを確認する。
   失敗したらここで止め、エラー内容を報告して修正する（ユーザーに丸投げしない）。

3. 現在 `master` 上で直接作業している場合は、変更内容がわかる名前で
   ブランチを切る（例: `news/2026-08-08`, `chore/xxx`, `fix/xxx`）。

4. 論理的な単位でコミットする。コミットメッセージはこのリポジトリの慣習
   （`news:` `chore:` `fix:` `feat:` などの prefix）に合わせる。`git log --oneline`
   で直近の傾向を確認してよい。`original-memo/*.md` の整形は `.githooks/pre-commit`
   が自動で行うため、手動での `npm run format` は不要。

5. `git push -u origin <branch>` する。

6. `gh` コマンドが使えれば `gh pr create --fill` でPRを作成しURLを報告する。
   使えない／認証されていない場合は、push済みである旨と手動でPRを開く手順
   （GitHubのURL）を案内する。

## 注意

- `master` への直接pushは日次ニュース自動生成ワークフロー以外では避け、
  PR経由を基本とする。ただし過去に直接pushで完了しているケースもあるため、
  リポジトリのルールで強制的に拒否されるわけではない。push が実際に拒否された
  場合のみ、ブランチ＋PRに切り替える。
- `git push` や `npm run build` が失敗した場合は、ユーザーに聞く前に
  まず自分でエラー出力全文を読んで原因を特定する。
