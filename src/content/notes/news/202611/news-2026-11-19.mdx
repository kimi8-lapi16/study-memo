## 楽天証券の不正アクセス、漏えい規模が最大1570万口座に拡大 テスト環境からの流出を確定

楽天証券は11月17日に公表した不正アクセスによる情報漏えいについて、対象範囲が当初発表時より拡大し、最大約1570万口座に達したことが11月18日までに分かった。

セキュリティインシデント・脆弱性案件(本日1件目、最大3件枠。17日発覚分の続報)。当初は部店コード・顧客コード・ログインIDのみが対象の最大約1125万口座と説明していたが、これとは重複しない形で、氏名・住所・資産情報などを含む最大約447万口座が新たに判明し、合計で最大約1570万口座に拡大した。また当初「漏えいの可能性がある」としていた内容について、調査の結果実際に漏えいしたことを確認したという。漏えい経路は11月11日にテスト環境で管理していた情報が外部へ流出したもので、楽天証券は通常は本番データをテスト環境に持ち込まないとしつつ、今回は特殊な事情でテスト環境にもデータを格納していたと説明している。ログインや取引に必要なパスワード・暗証番号の漏えいは確認されておらず、本件に起因する不正アクセス・不正取引も現時点で確認されていない。

## NGINX、HTTP/2処理の脆弱性2件を修正 静的ファイル配信のみの構成でも認証なしRCEを確認

NGINX開発チームは11月18日、HTTP/2のリクエスト処理に存在する脆弱性2件を修正した版を公開した。

セキュリティインシデント・脆弱性案件(本日2件目、最大3件枠)。「CVE-2026-123007」は2015年公開のNGINX 1.9.5から存在し、HTTP/2で送信可能なデータ量の計算誤りによりメモリが破壊されワーカープロセスが異常終了するおそれがあり、静的ファイルのみを配信する構成でも影響を受ける。もう一方の「CVE-2026-123633」は、クライアントからのHTTP/2リクエストをバックエンドへ転送するリバースプロキシ構成が対象で、1.19.7から存在し、接続数上限(`worker_connections`)に関係する解放済みメモリの参照が起こり得る。いずれもHTTP/2が有効で外部クライアントが直接接続できる構成が前提で、F5は両方をCVSS v4.0で9.2(Critical)と評価、検証したWizは認証なしでのリモートコード実行を確認したとしている。修正版はメインライン1.31.9、安定版1.30.7。設定の再読み込みだけでは古い実行ファイルが使われ続けるため再起動が必要で、すぐに更新できない場合は外部からのHTTP/2接続を無効化する回避策もあるが、gRPCなどHTTP/2を利用するサービスへの影響を事前に確認する必要がある。

<Note>CDNやWAFがHTTP/2をクライアントとの間で終端していれば一部の攻撃を防げる可能性があるが、バックエンドとの接続がHTTP/2であれば`CVE-2026-123633`の影響は残る。</Note>

## 今日のTips: PostgreSQL 11以降、デフォルト値付きカラムの追加でテーブル書き換えが要らなくなった

PostgreSQL 10以前は、`NOT NULL`なデフォルト値付きで`ALTER TABLE ... ADD COLUMN`を実行すると、既存の全行にデフォルト値を書き込むためテーブル全体を書き換えていた。巨大テーブルでは長時間のロックにつながり、運用上の鬼門だった。

PostgreSQL 11では、デフォルト値が定数であれば書き換えを行わず、カタログにデフォルト値を記録するだけで済むようになった。既存行を読み出す際にカタログの値を補って返す仕組みのため、追加自体は実質的に即時完了する。

```sql
-- PostgreSQL 11以降、書き換えなしで即時完了する
ALTER TABLE users ADD COLUMN plan text NOT NULL DEFAULT 'free';
```

<Tip>この最適化は`random()`のような揮発性(volatile)関数をデフォルトに指定した場合は効かず、従来どおり全行を書き換える。「定数かどうか」が分岐点になる点に注意する。</Tip>

参考: [PostgreSQL 11 Release Notes](https://www.postgresql.org/docs/release/11.0/)
