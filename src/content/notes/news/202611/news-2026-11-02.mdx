## Alpine Linux、GitLab最大深度脆弱性の攻撃を受けインフラを再構築 侵入有無は特定できず

Alpine Linuxプロジェクトは、前日のダイジェストで報じたGitLabの最大深度(critical)脆弱性(CVE-2026-97229)を突く攻撃を自社のGitLabインフラが受けたことを公表し、インフラを一から再構築したと発表した。

セキュリティインシデント・脆弱性案件(最大3件枠、本日2件目・続報)。攻撃は10月20〜21日に発生し、GitLabのCI/CDパイプラインで使われる正規表現コンパイラ「Onigmo」の整数オーバーフローを突くもので、GitLabは10月12日に修正版をリリース済みだった。Alpineは修正版への対応が遅れ、パッチ未適用の19.3.4を導入し、その後アップグレードした19.3.6でもRubyパッチを含まない独自コンテナイメージのため脆弱性が残っていた。攻撃期間中、攻撃者は悪意あるCI設定を送り込み8件のワーカークラッシュを引き起こし、一部は部分的に成功したが完全な成功には至らなかったとみられる。AlpineのGitLabコンテナイメージもダウンロードされており、サプライチェーン攻撃の準備だった可能性がある。10月27日までの調査ではリポジトリのコミットやパッケージ、リリースへの改ざんは確認されていないが、ログが欠落しており侵入によるコード実行を完全には否定できないとして、ユーザー情報・パスワードハッシュ・2FAシークレット・CI/CDシークレット・非公開プロジェクトの内容などが流出した可能性があるという。Alpineはこのためインフラを一から再構築し全パスワードをリセットした上で、利用者にもGitLabパスワードの再設定と、Rubyパッチを含む修正済みコンテナイメージ(`alpinelinux/gitlab:19.3.6`、10月27日公開)への更新を呼びかけている。

## 今日のTips: NestJSの`@Res()`、標準のレスポンス処理を無効化し`APP_INTERCEPTOR`等も効かなくなる

NestJSのコントローラーでは戻り値をそのままレスポンスにする標準方式がデフォルトだが、ExpressやFastifyのレスポンスオブジェクトを`@Res()`で注入すると、そのルートでは標準方式が自動的に無効化され、インターセプターや`@HttpCode()`・`@Header()`など標準方式に依存する機能が効かなくなる。

```ts
// 標準方式: インターセプターやAPP_INTERCEPTORが効く
@Get()
findAll() {
  return this.service.findAll();
}

// @Res()を使うと標準方式が自動的に無効化される
@Get(':id')
findOne(@Res() res: Response) {
  res.status(200).json(this.service.findOne());
}

// passthrough: true なら標準方式を維持したままネイティブAPIも使える
@Get('with-cookie')
findWithCookie(@Res({ passthrough: true }) res: Response) {
  res.cookie('seen', '1');
  return this.service.findAll();
}
```

<Note>`@Res()`を注入するとレスポンス送信の責任もアプリ側に移るため、`res.send()`等を呼び忘れるとリクエストがハングする。Cookieやヘッダーの操作だけがしたい場合は`passthrough: true`を使えば標準方式とインターセプターを維持できる。</Note>

参考: [Controllers | NestJS - A progressive Node.js framework](https://docs.nestjs.com/controllers)
