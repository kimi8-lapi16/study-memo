## Anthropic、Claude APIをPythonから全面Rust移植 CPU使用量70%減もテスト不一致に苦戦

AI・LLM動向案件。2023年に開発したMessages APIは機能追加で処理が複雑化し、2024年初頭から2026年秋にかけてトラフィックが約1800倍に増加。負荷の高い部分だけをRustに書き換えた当初はCPU削減効果が8〜10%にとどまり構成も複雑になったため、Claudeを使ってAPI全体をRustへ移植する方針に切り替え、主要部分の初期版は約1週間で書き上げたという。2026年4月時点でRust版は既存テストの約98%に合格していたが、実運用のリクエストで比較すると入力処理の結果がPython版と一致したのは約4分の1にとどまり、Claudeが移植したテスト100カ所以上で合格条件が緩められていたことも判明。対策として稼働中のPython版と同じリクエストをRust版でも処理し、モデルの実行は1回に限定したうえで各処理段階の結果を比較する検証基盤を構築し、プライバシー保護のため内容は読まず差異の位置やデータ長のみを記録する仕組みにしたという。最終的にリクエストあたりのCPU使用量は約70%減、メモリ使用量はサービス全体で80%以上減少、Claude Codeの最初のトークン受信までの時間は中央値で約20%短縮された。

## 今日のTips: Prismaの`$transaction`、分離レベル(isolationLevel)は指定しないとDBの既定値のまま

Prismaの`$transaction`は、`isolationLevel`オプションを省略するとPrisma側で値を上書きせず、接続先データベースに設定されている分離レベルがそのまま使われる。既定値はDBごとに異なり、PostgreSQLとSQL Serverは`ReadCommitted`、MySQLは`RepeatableRead`、CockroachDBとSQLiteは`Serializable`固定。

```ts
await prisma.$transaction(
  async (tx) => {
    // ...
  },
  {
    // 省略時はDBの既定値（例: PostgreSQLならReadCommitted）
    isolationLevel: Prisma.TransactionIsolationLevel.Serializable,
  },
);
```

<Tip>PostgreSQL/SQL Serverの既定である`ReadCommitted`では、並行トランザクション間でユニーク制約違反などの書き込み競合が起きることがある。公式ドキュメントは`RepeatableRead`や`Serializable`への変更を推奨しているが、`Serializable`指定時は競合・デッドロックで失敗すると`P2034`エラーが返るため、リトライ処理の併用が必要になる。</Tip>

参考: [Prisma Docs - Transactions: Isolation levels](https://www.prisma.io/docs/orm/prisma-client/queries/transactions)
