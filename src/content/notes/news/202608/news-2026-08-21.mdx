## Zimbra Collaboration Suiteの認証不要RCE脆弱性、実際の攻撃で悪用

メールサーバ製品「Zimbra Collaboration Suite」の脆弱性（CVE-2026-73570）が、実際の攻撃で悪用されていることがポーランドのCERT Polskaにより8月20日に報告された。

セキュリティインシデント・脆弱性案件（最大3件枠）。SNMP通知処理における入力サニタイズ不備が原因で、攻撃者は認証なしで細工したSMTP要求を送るだけでZimbraユーザー権限による任意のOSコマンド実行が可能になる。Shadowserverの追跡では脆弱性を持ちうるZimbraサーバが1万2100台以上インターネット上に公開されており、うちヨーロッパに4382台、アジアに4492台が存在するという。修正版10.1.20は7月20日に公開済みで、未適用の組織は早急なアップデートが求められる。

出典: [BleepingComputer](https://www.bleepingcomputer.com/news/security/critical-zimbra-rce-flaw-now-actively-exploited-in-attacks/)

## CISA、MLflowの重大SSRF脆弱性の悪用をKEVカタログで警告

米CISAは8月19日、機械学習基盤「MLflow」の脆弱性（CVE-2026-64849）を既知の悪用脆弱性（KEV）カタログに追加した。

セキュリティインシデント・脆弱性案件（最大3件枠）。DNS再バインディングを利用したSSRF（サーバーサイドリクエストフォージェリ）保護のバイパスが原因で、認証なし・SQLiteバックエンドといったデフォルト構成のMLflow Tracking Serverが対象。攻撃者はクラウドのメタデータサービスへアクセスし、AWSのIAM認証情報などを窃取できる。セキュリティ企業watchTowrによると、CVE ID割り当てから数時間のうちにインターネット上のMLflowシステムに対するスキャンが始まったという。対象バージョンは3.15.0未満。

## 今日のTips: `CREATE INDEX CONCURRENTLY`はトランザクションブロックの中で実行できない

PostgreSQLで本番稼働中のテーブルにインデックスを追加する場合、通常の`CREATE INDEX`は書き込みをロックしてしまうため`CONCURRENTLY`オプションを使うのが定石。ただしこのオプションには見落としやすい制約がある。

```sql
-- NG: トランザクションブロック内では実行できない
BEGIN;
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
COMMIT;
-- ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block

-- OK: トランザクションの外で単独実行する
CREATE INDEX CONCURRENTLY idx_orders_user_id ON orders (user_id);
```

<Tip label="▶ 補足">
`CONCURRENTLY`は書き込みロックを取らない代わりにテーブルを2回スキャンする（通常より低速・高負荷）。また処理が失敗すると`INVALID`状態のインデックスが残ることがあり、この場合はクエリからは無視されつつ更新のたびにオーバーヘッドだけが発生するため、`DROP INDEX`してから再実行する必要がある。マイグレーションツールを使う場合、自動でトランザクションに包まれてこのエラーになるケースがあるので、対象マイグレーションだけトランザクション無効化の設定が要る。
</Tip>
